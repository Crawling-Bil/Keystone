# Topology Builder

Draws the network from the neighbor tables already inside your device captures and exports a draw.io file.
Page: `/topology` (Analyze group). Design, algorithms and roadmap: `docs/modules/topology-design.md`.

## What to upload

Captures (`.txt`, `.log`, `.cfg`) or one or more `.zip` archives of them, up to 100 devices. A file may hold several devices' sessions one after another (a prompt such as `SW1#` or `<SW1>` followed by commands); it is split per device. ZIP member names are reduced to the file name, hidden and non-text members are ignored. Each capture should contain:

| Purpose | Cisco IOS XE / NX-OS | Huawei VRP |
|---|---|---|
| Links | `show cdp neighbors detail`, `show lldp neighbors detail` | `display lldp neighbor` (detail: address, description, duplex; `brief` still draws the links) |
| Port-channels | `show etherchannel summary` / `show port-channel summary` | `display eth-trunk` |
| vPC pairs | `show vpc` | - |
| Model, serial, stack | `show inventory`, `show version` | `display version`, `display device` |
| Management IP | running configuration or `show ip interface brief` | `display current-configuration` |

The collect lists in `static/collect-scripts/` already contain most of these commands.

Other vendors that are drawn since 0.6: a **FortiGate** configuration (`show full-configuration` or a backup file; since 0.7 each VDOM that holds data ports is its own firewall node) and an **F5 BIG-IP** (a `.ucs` archive, `bigip.conf` / `bigip_base.conf` or `tmsh list net self net vlan net route net trunk`; add a prompted capture of the same unit with `show net interface` and `show net arp` for port state, speed and ARP). A UCS and the capture of the same unit are merged into one device. Neither has a CDP/LLDP table, so their cables come from the neighbors' side, from ARP / MAC evidence and from descriptions written `HOST - port`. Since 0.7 a **Palo Alto** PAN-OS configuration (XML export, `show config running` or `set` commands) is drawn too, one firewall node per virtual system. A MikroTik file is still skipped with a reason.

## How the diagram is built

1. **Identity.** A neighbor is matched to a captured device by serial number, then chassis MAC, then short hostname (domain and `(SERIAL)` suffix removed), and last the management/interface IP. An IP that differently named neighbors share (TOPO-030) is skipped in that last step. Two captures with the same hostname but different serials are kept apart (TOPO-003).
2. **Links.** Port names are normalised (`TenGigabitEthernet1/1/1` = `Te1/1/1`, LLDP capability codes in front of a port id are dropped). Each device's "on my port X I see device Y port Z" rows are paired. Both ends agree: *confirmed*. Only one end reports it: *single-sided* (peer not captured, or CDP/LLDP off). The peer's own table says the port faces another device: *conflict*.
3. **Bundles and vPC.** Links whose ports belong to the same port-channel become one line labelled with the Po name, member count and protocol. A vPC peer-link (from `show vpc`) is blue. A port-channel whose members reach two different switches is marked multi-chassis and carries the vPC id.
4. **Roles and tiers.** Hostname words (AGG, TOR, FW, RT, AP, SWCO / SWDI / SWAC ...), then model, then graph shape. Rows from the top: edge routers and firewalls, then the switches by their hops from the core (see *Hierarchy: core, distribution and access*), then endpoints.
5. **Hosts (option).** MAC addresses from `show mac address-table` / `display mac-address` on edge ports (not port-channels or ports that face another network device), joined with the ARP table for the IP, become hosts. Virtual and multicast MACs (HSRP/VRRP, 01:00:5e...) are dropped. Up to three hosts on a port are drawn one by one, more become one "N hosts" node. They are always in `hosts.csv`; they are drawn only when "Draw hosts" is on.
6. **Routed links (option).** Two captured devices with addresses in the same /30 or /31 (same VRF) get a dashed blue line with the subnet. When a CDP/LLDP link already joins them on that interface the subnet is added to that link instead of drawing a second one. A device whose peer is not captured is still joined when another device's neighbor table advertises the peer address. Management and loopback interfaces are ignored.
7. **Endpoints.** Three or more access points, phones or hosts hanging off one switch become one node ("14 access points"); every port is still listed in `links.csv`.

8. **vPC view.** Each vPC pair (both switches captured, same row) gets a dashed frame titled `vPC domain N`. A bundle that reaches both switches of a pair, or leaves both, becomes one thick line labelled `vPC <id> · <members>x<speed>` with the Po names at the ends, so 62 cables between four pairs read as a handful of lines. The peer-link stays inside the frame. Device positions are those of the physical page, so a hand-tuned layout carries over. A pair whose two switches sit on different rows, or with another device dragged between them, keeps its physical lines. The diagram file holds the physical page and the vPC page (option), and the preview has a Physical / vPC toggle. Concept: https://www.cisco.com/c/it_it/support/docs/switches/nexus-9000-series-switches/218333-understand-and-configure-nexus-9000-vpc.html
9. **Speed.** Per port, the rating of the transceiver (`show interface transceiver`: `10Gbase-SR`, `SFP-H25GB-SR`, `QSFP-40G-SR-BD`, `1000base-T`) wins; otherwise the interface name says it (`Gi` 1 G, `Te` 10 G, `Twe` 25 G, `Fo` 40 G, `Hu` 100 G, Huawei `XGE`/`GE`); `Eth1/1` on NX-OS without transceiver data stays unknown. It is a rating, not the negotiated rate. Bundle labels read `4x10G LACP`; mixed members read `2x10G+2x1G`. "Style lines by rated speed" colours and thickens the lines by the fastest member (1G light blue, 10G blue, 25G purple, 40G green, 100G orange; dashed = not confirmed from both ends).
10. **Management links.** A link on a `mgmt` port is kind `mgmt`. By default it is left out of the picture (and out of the row layout) and stays in `links.csv`; untick the option to draw it thin and dotted.
11. **Devices behind devices.** A MAC learned on a port that faces a device nobody captured (a UCS fabric interconnect, a hypervisor uplink, a switch not yet collected) belongs to that device. These MACs are listed in `hosts.csv` with `behind`, summarised per port in `behind.csv` (MAC count, MACs with an IP, VMware and Hyper-V by MAC prefix, VLAN ranges), drawn nowhere and never counted by TOPO-007. VMware (`00:50:56`, `00:0C:29`, `00:1C:14`, `00:05:69`) and Hyper-V (`00:15:5D`) are hints only: an administrator can give a virtual machine any MAC. Prefix source: https://macaddress.io/faq/how-to-recognise-a-vmwares-virtual-machine-by-its-mac-address

## Adding to a previous run

`topology.json` holds the tables and a compact `state` block with every captured device (neighbors, bundles, vPC, speeds, MAC and ARP tables). Upload it under "Add to a previous run" next to new captures: the saved devices are kept, a new capture replaces the saved device with the same serial number or hostname, and the whole estate is rebuilt (links between old and new devices are confirmed). With no new captures it rebuilds the previous run with other options. Devices from the saved state are marked `previous run` in `devices.csv` and TOPO-022 lists them, because two captures taken on different days can disagree. The file is read as JSON only, size-limited, with types checked field by field; nothing in it is executed.

## Documentation pack

`keystone-topology-pack.zip` holds `topology-report.html`, one SVG per diagram page, `topology.drawio`, `topology.xlsx`, every CSV and `topology.json`. The report has no scripts and no external files: diagrams (both views), findings, device inventory, bundles and vPC, hosts behind uncaptured devices, one page per captured device (facts and ports) and the method and limits. Open it in a browser and print it to PDF (landscape A4, each device starts a new page). Everything that came from a capture is HTML-escaped.

## Reading the result

| Look | Meaning |
|---|---|
| Black line | Both ends report the link |
| Orange dashed | One end reports it |
| Red dashed | The two ends disagree |
| Blue thick | vPC peer-link |
| Grey box | Seen in a neighbor table, not captured |

Lines are routed around devices that sit in their path, parallel lines between the same two devices are spread apart, and devices inside each row are placed left to right in natural name order (A-Z first, then 0-9; `JKT-A2` before `JKT-A10`), so the sequence on the page is the sequence a reader expects. What hangs off one device (switches, access points, phones, PCs, collapsed nodes) stays together right under that device, and a device that only uplinks (a router or firewall) sits over what it serves, so the APs of switch A are never mixed with those of switch B and routers A, B, C stay side by side over their core. Lines may cross more than with an order chosen to minimise crossings; draw.io lets you move a device when that matters.

Downloads: `keystone-topology-pack.zip`, `topology-report.html`, `topology.drawio` (open in diagrams.net; Edit Data on any device or line shows serial, model, source file, link list, speed, vPC id and state), `topology.xlsx` (Summary, Devices, Links, Bundles, Hosts, Behind devices, Findings; cell text is never stored as a formula), `links.csv`, `devices.csv`, `hosts.csv`, `behind.csv`, `bundles.csv`, `findings.csv`, `topology.json`.

**Keep my layout.** Move devices in draw.io, save, and upload that `.drawio` as "Previous diagram" on the next run. Devices are matched by the `node_key` stored in the file, kept where you put them, and new devices are placed in free space. Only uncompressed draw.io files are read (File > Properties > Compressed off; the files Keystone writes are uncompressed); a DOCTYPE or external entity in the file is refused.

## Version 0.4: negotiated speed, wireless clients, Aruba CX

- **Speed source.** `show interface status` (Cisco, `a-` prefix = auto-negotiated) and AOS-CX `show interface` give the speed and duplex a port runs at; `links.csv` now has `speed_a/b` (running, else rated), `rated_a/b`, `duplex_a/b` and `port_state_a/b`. Bundle labels use running speeds. Only up ports carry a running speed.
- **Wireless clients.** MACs learned on a port that faces an access point (CDP capability `Trans-Bridge`, LLDP `W`, name or model rules) are counted as wireless clients of that access point: no TOPO-007 / TOPO-014 for them, `device.wireless_clients` in `topology.json`, and the Behind devices table lists the access point with role `ap`.
- **CDP capabilities.** `Capabilities:` of `show cdp neighbors detail` feeds the role classifier (a 3945 reporting `Router Source-Route-Bridge Switch` is a router, an AP reporting `Trans-Bridge` an access point).
- **CDP / LLDP on the same port.** When one neighbor is reported by both protocols under two names (Meraki and Cisco access points report a MAC in CDP and a name in LLDP), the two rows are merged instead of drawing two devices.
- **Aruba AOS-CX.** `show system` supplies model, serial, base MAC and AOS-CX version (own MAC is excluded from the host list); STP rows with role `Disabled` are no longer read as blocking (TOPO-009 false positive); `show interface` supplies speed, duplex, description and bundle. TOPO-013 does not ask Aruba/Huawei captures for `show cdp neighbors`.
- **TOPO-010** is not raised when the end without a bundle did not capture `show lacp` / port-channel summary: the bundle may exist there.
- **Preview.** Zoom (+ / - / fit), Ctrl+wheel, drag to move and "Open in new tab" for large diagrams.

## Version 0.5: logical IP view, inferred neighbors, endpoint options, label placement

- **Logical IP view** ("Diagram file contains" > "Logical IP view only"). Two devices that own addresses in the same subnet are joined by one green line labelled with the interface and address at each end (`Gi0/0/3 172.21.124.1/29` - `vlan153 172.21.124.2/29`). A subnet shared by more than two devices (an SVI VLAN, a LAN) is one yellow oval that every member connects to, labelled with the VLAN, VRF and description. Two devices that share more than three subnets (an aggregation pair with 30 SVIs) are drawn as one line "N shared subnets"; the tables list every address. Loopbacks, /32 addresses, `mgmt0`/OOB, `vmanage` and shut-down interfaces are not links. A subnet is matched by network address only, because VRF names are local to a device. A device nobody captured (an access point, a provider router) joins when an ARP table gave its address and the address falls inside a captured interface's subnet. Under the picture, every device with two or more interface addresses gets a table: interface, description, address/prefix, VRF, state (secondary addresses included). Use it to follow the route of a packet: device, interface, next subnet, next device. The page also exists in the SVG preview, the HTML report and the draw.io file (tables are HTML-table text cells you can edit). /31 point-to-point links are read as two-member subnets (RFC 3021: https://www.rfc-editor.org/rfc/rfc3021).
- **Neighbors without CDP/LLDP** (TOPO-027, low). **Order of trust: CDP/LLDP, then ARP, then MAC address, then port description.** A port that has a CDP/LLDP line is never touched. On any other physical port the first source that names a device wins: (1) ARP: an address on the port that belongs to a known device; (2) MAC address: every MAC learned on the port (at most 8) belongs to one device, found by its chassis MAC or through someone's ARP table; a port that also carries hosts says nothing; (3) the interface description. When the lower sources agree with the chosen one they are added to the evidence (`ARP+DESC`); when they name another device the finding says so (TOPO-028). Only when no known device is found does a lone ARP peer on a routed port, or a description that looks like a device name, create a new grey box. In detail, a routed physical port with no CDP/LLDP line gets a teal dashed line when (a) its interface description names a device and port (`WANR2 G0/1/2`, `to JAS-1-LT-1A`; the name is matched to a captured device first, by full name then by distinctive fragment, otherwise a new grey box is drawn) and/or (b) the ARP table on that port holds exactly one peer whose address belongs to a captured device or sits on a /29-/31 link (ARP maps IPv4 address to MAC address: https://www.rfc-editor.org/rfc/rfc826). ARP tables of every VRF (`show ip arp`, `show ip arp vrf <name>`) are read. Providers named in a description (LINTASARTA, TELKOM, ISP, MPLS, INTERNET...) become cloud boxes. Descriptions that name servers, PCs, printers, cameras, ATMs, phones or other endpoints never create a device; a pair already joined by a CDP/LLDP line is skipped. The evidence (`ARP`, `DESC`) is in the line's tooltip, `links.csv` and the finding. This is evidence, not proof: a stale ARP entry or a wrong description can mislead, so the line is dashed teal and the finding says what to verify. Switch off with "Infer neighbors from ARP and port descriptions".
- **TOPO-028 (low): description names another device.** A port whose CDP/LLDP neighbor (or inferred neighbor) is not the device its description names, for example `Gi2/0/45` described as `AP-6` but facing `AP-7`, or a description that still names the old switch after a move. The line follows the device data; fix the description or the cabling.
- **Topology name and creation time.** The optional box "Topology name" prefixes every download (`Lab-DC-topology.drawio`, `Lab-DC-links.csv`, `Lab-DC-keystone-topology-pack.zip`); letters, digits, `.`, `_`, `-` are kept, spaces become `-`, 60 characters at most; empty keeps the current names. The name is also the title of the HTML report and of every draw.io page, and every draw.io page shows `Topology Created at Date YYYY:MM:DD - Time HH:MM:SS` (local time of the Keystone computer) under it, above the devices.
- **Roles from CDP capabilities.** `Router Switch` is a layer-3 switch, `Router Source-Route-Bridge` a router, `Trans-Bridge` / `WLAN` an access point. AOS-CX LLDP descriptions such as `HPE ANW JL724B ML.10.16.1020` are split into model `JL724B`, version `ML.10.16.1020`, vendor Aruba, and Aruba/HPE `JL` models are switches. Previously an Aruba CX switch seen only by its neighbor was drawn as a router. F5 BIG-IP, NetScaler, `LB/SLB/GSLB/LTM/GTM/ADC` names get the load-balancer role and icon.
- **Exclude IP phones and PCs.** Leaves phones, hosts and servers out of the pictures (and the boxes that stand for several of them) so only routers, firewalls, load balancers, switches and access points remain; tables and CSV still list them. **Collapse phones and hosts** now folds only phones and hosts; **Collapse access points** is a separate option, so each access point can be drawn with its own hostname, model and IP address in a detailed diagram.
- **Grouping by the first one, two or three hostname words** (`JKT`, `JKT-A02`, `JKT-GD1-LT1`). On the overview page each group is a black frame. The group with the most lines to other groups sits in the middle cell of a square grid, the groups linked to it most are next to it, the rest further out, "Other devices" last; cells are as wide as the widest frame of the column, so frames never overlap. Inside a group, the device with the most connections of a row is moved to the middle of that row when that adds no line crossing.
- **Option defaults and the form.** On: exclude IP phones/PCs/servers, collapse phones and hosts (hidden while exclude is on), show port names, infer neighbors, add routed /30 and /31 links, leave management links out. Collapse access points is on too (clear it to draw each access point on its own). Off: draw end hosts (hidden while exclude is on). The form lists the topology name first, then the options, then the device captures; the diagram settings and the earlier-work files are in the right column.
- **`run-settings.txt`.** Every run writes the options it was built with (each option on/off with its label, grouping, file contents, line style, whether a previous run or layout was used), the topology name, the creation time and the tool version. It is in the pack, a separate download, `topology.json` (key `build`) and the HTML report (section Build options). Attach it to a question or a bug report instead of describing the page.
- **Line style** defaults to rated speed (1G, 10G, 25G, 40G, 100G).
- **Spacing and label placement.** The horizontal step grows with the longest label, rows get more room when many lines leave a device, and long endpoint rows wrap into staggered sub-rows. Each port, bundle and subnet label tries several distances and offsets along its own line and takes the first position that is free of icons, hostname text and other labels; the SVG preview and the draw.io file use the same positions. Port lists longer than 30 characters are shown as `N ports` (full list in the tooltip, tables and draw.io data). Labels have a white outline so they stay readable over lines.
- **AOS-CX.** `interface vlan 130` (with a space) is a routed interface in the Switch Analyzer, so its address reaches the IP view.

## After 0.5: automatic sites, findings by device

- **Grouping "Automatic"** (the first choice of the form). Fewer than 30 devices stay on one diagram. A larger network is grouped by the shortest hostname prefix (one, two or three words) whose groups each hold at most 40 devices, with at most 40 groups and at least two groups of two or more devices; the result is an overview plus one page per site. Devices nobody captured (a firewall, a server, a stray MAC name) never form a site of their own: they go to "Other devices". When no prefix gives readable sites the diagram stays whole. Choose "One diagram" or a fixed prefix to override it. `run-settings.txt` and the report name the grouping that Automatic applied.
- **Findings by device.** A roll-up of the findings per device, worst first: medium, low and info counts and the finding ids (`TOPO-002 x2, TOPO-010`). A link finding counts for both ends; a device that was only seen by a neighbor shows `captured = no`, which is where to collect next. It appears at the top of the Findings tab, as the "Findings by device" table in the report (and a "Findings that name this device" table on each device page), as the "Findings by device" sheet of `topology.xlsx` and as `tables/findings-by-device.csv` in the pack. Only devices with at least one finding have a row.

## Limits of version 0.5

- The IP view shows what the captures say: static or DHCP addresses on interfaces, ARP entries and descriptions. It does not read routing tables, so it shows which devices share a subnet, not which route a packet takes. HSRP/VRRP virtual addresses are listed in the tables when the interface carries them as secondary addresses; they are not drawn as members.
- Automatic grouping only reads hostnames; a network whose names do not start with a site code (for example role first: `SW-JKT-1`) is split by the second or third word when that gives readable sites, otherwise it stays one diagram.
- **Smart sites** (`sites.py`; the choice "Sites, smart", and what Automatic uses when it is better). `detect(graph, take)` starts from the first `take` words of the hostname, as the prefix grouping does, and corrects it with what the graph shows. It never reads a list of site names; every rule is a constant at the top of the module and has a mutation test.
  - **Glued site code** (`learn_codes`, `site_words`): `HQWANR1`, `HQEDGNX1`, `HQKSR1` have no separator. A code is the shortest start (2 letters or more) of a first word that at least 3 longer first words share (`CODE_MIN_HEADS`), which they continue with at least 3 different letters (`CODE_MIN_NEXT`: a role word follows, not a counter), and whose devices are cabled to each other (at least a quarter of them, and 2: `CODE_MIN_CABLED`). `SW1 SW2 SW3` or four unrelated firewalls that start alike give no code.
  - **Zeros and case** (`_pad`, `words`): `LT02` is `LT2`, `dea-off` is `DEA-OFF`.
  - **Mistyped names** (`_merge_near_names`): two sites whose names differ by one letter in one word of 4 letters or more (`NEAR_MIN_LEN`), never a digit, and that have a cable between them are one site.
  - **A device with a name of its own** (`_adopt_by_word`, `_adopt_by_cable`): a device in "Other devices" joins the one site whose name has the same word (`MIKROTIK-JAS` and `KCU-SENAYAN-JAS`) unless its cables lead to another site; a name family of 2 network devices or fewer (`SMALL_SITE`) whose cables all lead to one site of 3 or more (`HOST_SITE_MIN`) joins it (a WLC named after its vendor).
  - **One name, two sites** (`_split`): a site of 4 network devices or more (`SPLIT_MIN_SITE`) whose network devices fall into parts with no cable between them is split when each part has 2 or more devices, one captured (`SPLIT_MIN_PART`). Each part is named by the words its devices share (`JKT-GD1`, `JKT-GD2`), end points follow their switch.
  - **One site, one diagram** (`one_site`): when the plain prefix makes two or more sites but the cables and names make it one (a WLC named after its vendor and its access points), Automatic returns "none" instead of the prefix.
  - **Automatic** (`layout.auto_mode`): the plain prefix is the answer when it gives the same sites as the smart grouping; the smart sites are used when the prefixes give nothing readable or when they put more network devices in a real site and leave fewer in "Other devices". A network of fewer than 30 devices stays one diagram, unless the plain prefixes show no readable sites, 15 devices or more are drawn and two sites each have 3 captured network devices (`SMART_MIN_CAPTURED`, `SMART_MIN_DEVICES`).
  - **Floors of one building** (`PEERS`, `_is_peer`, `_join_by_shared_uplink`, `joined`, `CONNECTED_SPLIT_MIN`, `CONNECTED_SHARE`): siblings that differ only in the last word (JKT-A08, JKT-A09) are peers and are not merged into the aggregation floor by a cable; parts of a site that hang from one captured switch are one site; a building whose sites are cabled together (80% or more) is cut by the plain first words until it holds 100 devices or more, and then by the smart sites. A site is named as most of its devices spell it.
  - **Role first, site second** (`learn_leads`, `LEAD_MIN_DEVICES` 3, `LEAD_MIN_SITES` 3, `LEAD_DOMINANT` 0.6): `SW-JKT-1`, `RTR-JKT-1`, `FW-BDG-1` have the role before the site. A first word is a role (a lead) when several first words are followed by the same site words (letters, not counters: `SW1`, `SW2` is one word) and there are more site words than first words, or when one first word starts most names in front of 3 or more site words that are not role words themselves. The lead is dropped from the site name (`^SW` in the learned codes), and Automatic returns Sites, smart when the plain words would make a page per role and site.
  - **Role first, floor second** (`sites._learn_unit_leads`, `ROLE_WORDS`, `LEAD_MIN_UNIT_DEVICES` 2): `SW-A02-1`, `RTR-A08-1`, `SW-LT3-2`. A role word (SW, RTR, FW, AP, CSW, DSW, ASW, LEAF ...) in front of at least 3 different floor or building words (letters and a number, each naming 2 devices or more, at least 2 per role) is a lead and every such word is a site of its own, although the stem comparison of the first evidence sees A02 and A08 as one word. It never applies after a first word that is not a role (`KCU-LT1`, `BDG-LT1` are cities with floors), and `SW1`, `SW2` after a site stay counters.
  - **Site rules** (the box under Grouping; `parse_rules`, `apply_rules`): `Name = start, start`, one line per site; a device whose hostname starts with one of the starts (case and spaces ignored, first rule that fits) is in that site, the end points of the switches that moved follow them; used by every grouping except One diagram; `RULES_MAX` 60.
  - **Layout check** (`layoutscore.py`): per page the crossings of lines, the lines that run through another icon, and the line length, all on the lines as they are drawn (a line routed around a box or into a comb is scored on its bent path from `Page.routes`; any other line is the straight segment between two icons), with a cost (crossing 1, line through an icon 5, 1,000 px of line 1); run-settings.txt prints it, `settings['layout_check']` keeps it, and `tests/test_topology_layoutscore.py` keeps the demo sets within a budget.
  - **A3 print set** (`report.build_print_set`): `topology-print-a3.html`, one sheet per diagram page scaled to one A3 landscape sheet; open in a browser and print to PDF (A3, no scaling).
  - **A device tied to a row mate** (`_pull_to_heavy_peer`, `PEER_TIE_MIN` 6): a device of a row with 6 or more links to another device of the same row, and more than to anything above it, stands right after that device (a server NIC cabled to two ToR switches and the rack switch that shares it), wishing a place between the two in proportion to the cables; the device with more weight upward keeps its place. Without such a tie a row is unchanged.
  - **Neighbour floors on a site page** (`GHOST_ROW_MAX` 8, `layered(ghosts=)`): devices of other sites drawn on a site page because a cable leads to them stand in one row; when that row holds more than 8 of them it is dealt out over staggered lines (as a long row of end points is), so the aggregation floor of a building with twenty floors is not ten thousand pixels wide. Cisco campus design reference: https://www.cisco.com/c/en/us/td/docs/solutions/Enterprise/Campus/HA_campus_DG/hacampusdg.html
  - **Why Automatic chose** (`layout.auto_reason`): one or two plain sentences, shown under the results, written as `Why:` in run-settings.txt and returned as `group_reason`: one diagram (few devices, or one cabled site), one place cut into floors or areas ("One place (JKT) ... JKT-A15 (17), JKT-A02 (12)"), or several separate sites ("HQ (27), KCU (17)"), with the largest names and sizes, and whether the hostname words, the cables or both told them apart. Multi-site design reference: https://www.cisco.com/c/en/us/td/docs/solutions/CVD/SDWAN/cisco-sdwan-design-guide.html
  - Real example (the PANIN branch captures): the plain prefixes gave six one-device "sites" for the head quarter and one for the branch; the smart grouping gives HQ and KCU. Design reference for access / distribution / core as one site block: https://www.cisco.com/c/en/us/td/docs/solutions/Enterprise/Campus/HA_campus_DG/hacampusdg.html and for a multi-site WAN with branches: https://www.cisco.com/c/en/us/td/docs/solutions/CVD/SDWAN/cisco-sdwan-design-guide.html
- A very large VLAN (more than 24 SVI members) is drawn with the first 24 members; the tables list all of them.
- Inferred neighbors need ARP, a MAC table or descriptions to be in the capture (`show ip arp`, `show ip arp vrf <name>`, `show mac address-table`, `show running-config`); a router captured without them stays without neighbors. MAC evidence only works for devices whose chassis MAC is reported or whose address appears in an ARP table of a captured device.

## Limits of version 0.4

- The vPC view needs both switches of a pair in the capture set; a pair with one switch missing is drawn as a normal switch and TOPO-021 names it. MLAG pairs of other vendors are framed only when the capture tells the builder about the pair (today: Cisco vPC).
- Rated speeds come from the transceiver or the port name (transceiver data is required for NX-OS `Ethernet` ports); running speeds only from `show interface status` / AOS-CX `show interface` and only for ports that are up.
- The saved state grows with the MAC and ARP tables (about 0.5 MB for six Nexus switches); files above 120 MB are refused.
- PDF is produced by printing the HTML report in the browser; Keystone itself does not render PDF.

- LLDP identity (chassis ID, management address, system serial) is read for Cisco IOS XE and NX-OS, Huawei VRP and ArubaOS-Switch detail output. Other vendors keep neighbor name and ports, so identity falls back to hostname.
- Hosts and routed links depend on the MAC, ARP and interface-address commands being in the capture; the Devices table shows which captures have CDP, LLDP and a MAC table.
- Routed links in the physical view are inferred only from /30 and /31 networks; larger shared subnets (SVI/VLAN segments) are drawn in the logical IP view.
- No live CDP crawl; Keystone reads captures only.
- The preview is a simplified drawing; the `.drawio` file is the deliverable. In very dense tiers a few lines can still cross, which draw.io lets you re-route by hand.

## Version 0.5a: L3 views (delivered)

Menu "Diagram file contains": L2 - Physical and vPC view, L2 - Physical view only, L2 - vPC view only, L3 - Logical view only (shared subnets, interface addresses), **L3 - Logical and Route**, and **L3 over L2**.

- **L3 - Logical and Route.** Built by `l3engine.build` from every captured device: interface addresses (`Device.l3`), interface state, routes grouped by next hop, OSPF / EIGRP / BGP neighbors, tunnel interfaces and SD-WAN BFD sessions (`Device.l3facts`). Edge kinds: `p2p` (two devices in one subnet), `segment` (three or more), `tunnel`, `overlay` (SD-WAN: one edge per site pair, BFD sessions up/total, colours), `peering` (a routing session or a next hop that no shared subnet explains) and `gateway` (a neighbor or next hop inside a connected subnet that nobody captured). A next hop or neighbor that no capture explains is kept in `L3Model.unresolved`, not drawn. A captured router, firewall or load balancer without any edge still stands on the page; a switch whose only routed address is its management interface (at most one default static route, no routing neighbor, tunnel or first-hop redundancy: `l3page._management_only`) does not, so the page is not widened by a row of access switches. They stay in the tables and on the physical pages.
- **Evidence and state.** Each edge lists the sentences that prove it. `up` = the interface is up/up or a routing neighbor is FULL / Established, `down` = an interface is down or a neighbor is not up, `configured` = only the configuration says so. Solid line = up, dashed = configured, red = down. The view shows routing intent (what the routing tables and interface states say), not measured traffic.
- **Look of a line.** Colour = VRF (a stable palette, dark grey = global table), SD-WAN overlay purple, global-table tunnel teal. Label: interface and address at each end, then `VRF`, subnet and the aggregated routes using the line (`OSPF default + 12 prefixes`).
- **Router captures without CDP/LLDP.** `service.read_devices` builds a device from the router reader (`l3facts.device_from_facts`) when the switch reader cannot use the file, so SD-WAN edge routers and WAN routers captured with `show` commands only appear on the L3 pages. The L2 pages show them as devices without links.
- **Provider clouds** (`l3cloud.py`). `classify` looks for what an access link faces: 1) rules typed in the "Provider hints" box, 2) transport words and provider names in the interface description, VRF name and CDP/LLDP neighbor name (`mpls`, `metro`, `internet`/`inet`, `lte`, ...), 3) the SD-WAN colour of the tunnel interface on that port. The colour names are the Cisco Catalyst SD-WAN colour list (default, mpls, metro-ethernet, biz-internet, public-internet, lte, 3g, red, green, blue, gold, silver, bronze, custom1-3, private1-6; https://netascode.cisco.com/docs/data_models/sdwan/policy_objects/color_list/); `mpls`, `metro-ethernet` and `private1..6` are the private colours. A typed rule that disagrees with the description wins; a colour that disagrees with the description is added to the evidence as a disagreement. One cloud per transport and provider (`CLOUD:mpls:telkom`) is shared by all sites; each edge keeps its gateway address. Rule syntax: `what = type [provider]`, what = `DEVICE INTERFACE`, an address or subnet, or a keyword; type = mpls, internet, metro, lte, private.
- **Click panel and tables** (`l3tables.py`). Every line has an ID `L3-nn`, a sentence (`meaning`), the evidence and the routes that use it; the same facts are in `l3-links.csv`, `l3-routes.csv`, the workbook sheets `L3 links` / `L3 routes` / `L3 unresolved`, the report section "L3 links" and the draw.io attributes.
- **L3 over L2** (`l3over2.py`). `underlay(graph, model)` maps every L3 edge to the physical connections that carry it (port lookup incl. sub-interfaces, shortest chain of captured cables for SVIs / peerings / segments, transport ports for the overlay, the facing port for provider links). The page reuses the physical page (same positions, shifted down 240 px when clouds or segments need a row above), copies each cable with `l3 = {role: "under", carries, colour, width}` (thick and coloured when it carries something, 1.5 px grey otherwise) and adds each L3 edge as a sampled Bezier arc bowing alternately to both sides when several links join the same two devices.
- **Key addresses on L2 lines** (`l2ips.py`): `Link.a_ip` / `b_ip` and `Connection.po_ip_a` / `po_ip_b` are filled from the interface addresses (`Device.l3`) of the port or the port-channel and appended by `labels.end_texts`.
- **Curved lines** (`scene.curve_routes`): the single bend point of a routed line becomes the middle of a quadratic Bezier (control point 2*via - (a+b)/2) sampled at 16 points; the SVG preview and the label placement follow the samples, draw.io gets every 4th point with `curved=1`.
- **Path trace** (`l3trace.py`). `trace_data` writes the interfaces, routes (with prefixes), address owners and the route-to-line map of a build to `_trace.json` in its export folder; `trace(data, source, destination, vrf)` follows connected subnets and longest-prefix routes hop by hop (max 16 hops, loop detection) and returns the hops and the line IDs to highlight. Endpoint: `POST /topology/api/trace {export_id, source, destination, vrf}`. Limits: only the best routes of a capture are known, equal-cost alternatives are reported but not followed, no policy routing / ACL / NAT / SD-WAN data policy.
- **SD-WAN overlay table** (`l3tables.overlay_table`) and **How to read** (`howto.py`, one source for the tab, the report and the draw.io page).
- Documentation used: Cisco SD-WAN command reference https://www.cisco.com/c/en/us/td/docs/routers/sdwan/command/sdwan-cr-book.pdf (BFD sessions, control connections, OMP), RFC 3021 for /31 links https://www.rfc-editor.org/rfc/rfc3021.

## Version 0.6: multi-site L3

- **Default view** is L3 over L2 (`routes.DEFAULT_VIEW`).
- **Branch focus** (`l3focus.py`). `Focus(mode, sites)` decides which remote SD-WAN sites `l3engine` draws: `captured` (default) draws only sites whose system IP belongs to a captured device, `all` draws a node for every BFD site, a typed list (`parse_sites`: site ID or system IP equal, host name by part) draws exactly those. Sites not drawn are kept in `L3Model.hidden` and summarised by one cloud (`SDWAN:more`, "+N SD-WAN sites") joined to each hub. `l3tables.overlay_table(graph, focus)` still lists every session with `on_the_picture`; `overlay_sites_table` lists every remote site for the picker (`l3-sdwan-sites.csv`). Form fields `overlay_sites` and `focus_sites`.
- **FortiGate** (`fortidev.py`): `forti_extract.extract(parse_forti(text))` reduced to a `Device`: VDOM = `vrf`, aggregate / redundant = `bundles`, `parent` and `vlan_id` of sub-interfaces, alias = description, static routes by VDOM and next hop (transparent VDOMs skipped), BGP neighbors, IPsec phase-1 tunnels. FortiOS references: virtual domains https://docs.fortinet.com/document/fortigate/7.4.7/administration-guide/597835/virtual-domains, interfaces https://docs.fortinet.com/document/fortigate/7.4.7/administration-guide/822100/interface-settings.
- **Switch L3 facts** (`l3switch.py`): routes (grouped by next hop, connected and local routes skipped), OSPF / BGP neighbors, ARP, HSRP / VRRP groups from the Switch Analyzer result; `merge` fills what the router reader did not read. NX-OS unicast routing guide https://www.cisco.com/c/en/us/td/docs/dcn/nx-os/nexus9000/104x/unicast-routing/cisco-nexus-9000-series-nx-os-unicast-routing-configuration-guide-release-104x.html, HSRP https://www.rfc-editor.org/rfc/rfc2281, VRRP https://www.rfc-editor.org/rfc/rfc5798, AOS-CX IP routing https://arubanetworking.hpe.com/techdocs/AOS-CX/10.13/HTML/ip_routing_cx_10.13/index.html.
- **Grouping** (`l3engine.group_parallel`, `group_gateways`): see the changelog; `L3Model.drawn()` returns the lines of the picture, `L3Model.edges` keeps every edge for tables, trace and click panel.
- OSPF neighbor election and 2-WAY: RFC 2328 https://www.rfc-editor.org/rfc/rfc2328.
- **Inferred cables** (`inferred.py`): a pair with no captured (CDP/LLDP) cable gets one inferred cable per distinct port pair that the ARP / MAC / description evidence names; a pair that already has a captured cable is skipped.
- **Layout of L3 over L2** (`l3over2.py`): extras (clouds, shared subnets, remote sites) are stacked in at most `MAX_ROWS` rows of `ROW_STEP` points; the physical cable routes are shifted with the devices; the underlay of a VLAN or sub-interface is found by walking `parent` interfaces (loop-safe).
- **Provider clouds on the L3 route page** (`l3page._place_with_clouds`). The clouds stand in the top row (`layered`, tier -1) and each may stand 0, 1 or 2 steps (`CLOUD_STEP` = 150 px) higher: the cost is the straight length of the lines to its devices plus `CLOUD_HIT` (400 px) for every line that runs through another node or its caption; one cloud at a time takes the height that lowers the total (3 passes). Without this a provider serving both ends of a wide page had its line sent over the top of the row by `scene._route`. Provider links on BGP: https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/configuration/xe-17/irg-xe-17-book/configuring-a-basic-bgp-network.html
- **WAN band on the L3 over L2 overview** (`l3over2._open_wan_band`). A cloud whose devices stand in two or more site boxes is placed in the free strip between two rows of boxes instead of above the page. The strip nearest the mean y of the devices those clouds serve is chosen; it grows by `2 * BAND_AIR + rows * BAND_ROW` minus its own height (`BAND_AIR` 150, `BAND_ROW` 170), everything at or below its middle moves down by that amount (devices, boxes, end boxes and route bends), and each cloud takes the mean x of its devices, at least `BAND_SPACING` (250) from the next cloud of its row; more than `BAND_MAX_ROW` (5) clouds use two rows. Fewer than three boxes: unchanged. The other extras (shared subnets, remote sites) are placed by `satellites.place` with the band clouds as fixed obstacles. Design guide: https://www.cisco.com/c/en/us/td/docs/solutions/Enterprise/Campus/HA_campus_DG/hacampusdg.html Which strip: `_open_wan_band` tries every strip (`_gap_page`) and the clouds above the page, scores each with `_band_cost` (length of the straight lines to the devices plus `BAND_HIT` = 400 px for every device a line runs through) and keeps the lowest.
- **BIG-IP** (`bigipdev.py`): `bigip_extract.extract(parse_tmsh(config))` plus `bigip_runtime.gather` reduced to a `Device` with `role_hint = "loadbalancer"`: a self IP is a routed interface (VLAN name and tag in the description / `vlan_id`, the VLAN's member port or trunk as `parent`), a floating self IP (traffic group other than local-only) is reported as an `fhrp` group so a next hop on it resolves to the pair, a route domain (`%N`) is a VRF, a trunk is a bundle, `net route` objects are grouped by route domain and gateway. UCS upload: `ingest._ucs` (streamed by `bigip_ucs.read_upload`); UCS + capture of the same unit: `service._merge_f5` (`bigip_ucs.merge_same_unit`). F5 references: tmsh `net self` https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/net/net_self.html, `net route-domain` https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/net/net_route-domain.html, `net trunk` https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/net/net_trunk.html. A FortiGate, a Palo Alto firewall or a BIG-IP is not asked for CDP / LLDP commands (TOPO-013 skips it; TOPO-008 becomes an info row).
- **Reading cache** (`service._read_one`, `_CACHE`): sha1 of the file name and content, 24 captures, deep-copied per build, so a changed option or SD-WAN site list does not re-read the captures.

## Version 0.7: every view in one file, framed end points, star layout, one firewall per VDOM / vsys, F5 map

- **All views** (`service.all_views_order`, option value `all`, now the default of the form). One build writes the draw.io file, the ZIP pack and the report with every view as its own page, in the order an engineer reads them: L3 over L2, L3 route view, IP view, physical view, vPC view (only when the captures hold a vPC pair) and the F5 map (only when a BIG-IP is uploaded). A view with nothing to draw is absent; the physical pages always exist, so the list is never empty. A single view can still be chosen.
- **Group end points under the same switch** (option `group_endpoints`, default on). When end points are drawn one by one (neither "Exclude" nor "Collapse" is ticked) the end points of each switch sit in one frame titled with the switch's host name (`scene.endpoint_boxes`). A switch with a single end point is not framed (`layout.BOX_MIN`), a dual-homed end point stays outside every frame, frames never overlap (`BOX_GAP`) and have at most `BOX_COLS_MAX` icons per line. The frames are in the SVG preview and in draw.io, and a layout kept from an earlier file keeps them. Without frames the switch layout is exactly the old one. The grouping by hostname prefix is independent of this option.
- **Star layout of router pages** (`layout.star_applicable`, `_star_sweeps`). A page with at least `STAR_MIN_ROUTERS` (3) routers, firewalls and load balancers, two of them captured, is ordered by up-and-down barycenter sweeps scored by line crossings: routers nobody captured sit in the outside row with the providers, the two units of a firewall or load-balancer pair stand next to each other (`ha_pairs`; one over the other at the end of a wide row that also holds other devices; a row of nothing but pairs keeps them side by side), three routers that all talk to each other form a triangle rather than a line through an icon, and rows never put two icons on one spot. A page of switches keeps the layout it always had. On the L3 over L2 page provider clouds, shared subnets, gateways nobody captured and remote SD-WAN sites are placed on free spots round the devices they join (`satellites.py`), the best connected first, instead of in a row.
- **One firewall per VDOM / vsys.** A FortiGate with several working VDOMs is one node per VDOM named `HOST [vdom]`, each with its own interfaces, routes, BGP neighbors and IPsec tunnels. A management-only root VDOM is not a node (its management address stays with the first node); a single working VDOM stays one plainly named device. An inter-VDOM link between two VDOMs is a cable between their nodes, inside one VDOM it draws nothing. A **Palo Alto** (`panosdev.py`) is one node per virtual system, the virtual router is the VRF, a VLAN sub-interface knows its parent port and its zone is the role. A neighbor's CDP/LLDP cable lands on the node that owns the remote port (`Device.unit_ports`, `graph.pick_unit`); an unknown remote port falls back to the first node, and a port description written `HOST - port` is matched by the same rule. Reference: https://docs.paloaltonetworks.com/pan-os/11-1/pan-os-admin/virtual-systems/virtual-systems-overview. Aggregate-ethernet interfaces are not read yet; their members are drawn as separate cables.
- **F5 map view** (`f5page.py`, view `f5map`). One page per BIG-IP built like the Load Balancer Analyzer's network map: virtual servers (wide IPs for BIG-IP DNS) round the BIG-IP in four blocks (left, right, top-left, top-right; at most eight in a side column, the rest goes on top), the pools below as frames with their members inside (a pool used by several virtual servers is drawn once), one box per node (member IP) below the pools. Colours follow the BIG-IP status icons; "configured and monitored" is shown when the capture holds no `tmsh show ltm` output. Tables under the picture: VLANs with tag, ports and self IPs, and the interfaces with state and speed. Reference: https://techdocs.f5.com/kb/en-us/products/big-ip_ltm/manuals/product/big-ip-local-traffic-management-basics-14-0-0/01.html
- **vCMP.** A vCMP host configuration is one load-balancer node per guest (`bigipdev.guests`): name, management address, VLANs, cores per slot, state and image from the host. A neighbor's cable lands on the guest whose VLANs ride the remote port; the guest's own UCS replaces its stub (`service._drop_replaced_guests`). A shared port goes to the first guest that uses it. Reference: https://techdocs.f5.com/kb/en-us/products/big-ip_ltm/manuals/product/vcmp-administration-viprion-13-1-0/6.html
- Known limits: a lone LTM's physical page is still a single box; a VDOM / guest without any neighbor is an isolated node; no LLDP is read from an F5; Palo Alto aggregate-ethernet is not read.
- Tests: `tests/test_topology_v07.py`, `tests/test_topology_v07_units.py`, `tests/test_topology_v07_f5.py` (synthetic data only).

## Version 0.8: uplink routers on top, router chains, four-switch box, end points under their switch, assumed F5 neighbors

- **Uplink routers** (`layout.uplink_routers`). A router nobody captured, linked to a captured router of its own row and to nothing below it, goes one row up (a star layout lifts such routers itself, `layered`). Physical page, L3 over L2 (`l3over2` marks the satellites of such a router `above`), L3 route page, IP view and draw.io share the positions.
- **Router chains** (`layout._star_orders`, `_crossings`). The score of a row order is crossings plus, for every line between two devices of one row, the devices standing between its ends. The main row (2 to `STAR_PERM_MAX` = 6 devices) is tried in every order (`STAR_PERM_EDGES` = 160 lines: above that the sweeps alone decide), mirror images and orders that split an HA pair are skipped, the other rows follow by barycenter.
- **VDOMs without a cable** (`layout.unlinked_siblings`). The VDOMs, vsys and vCMP guests of one chassis (`graph.chassis_units`) are separate devices. One with no cable on the page took the row its role gives and stood far from its siblings; it now takes the row of the sibling with the most cables and is linked to it for the order of the row only (nothing is drawn), so it stands next to it.
- **Rows from the outside in** (`layout.outside_in_rows`, star pages only). The role rows put every core above every distribution switch and every router above everything. When a cable shows the opposite (an edge switch pair between the WAN routers and the core ranks lower by role than the core it feeds), the rows of the page are counted in hops from the routers and clouds instead (`depth_row`): outside, edge, core, zones, access. Cables to end points and to shared-subnet nodes do not count as hops. A page whose role rows already agree with its cables is not touched. On the multi-site head quarter page this takes line crossings from 34 to 14. Reference for the layered design it follows (core, distribution, access): https://www.cisco.com/c/en/us/td/docs/solutions/Enterprise/Campus/HA_campus_DG/hacampusdg.html
- **Four-switch box** (`layout.find_meshes`, `mesh_tiers`). Four network devices of one row in which every device of one side is linked to both of the other side and both sides are twins (vPC / MLAG peers, or the same model with names that differ only in their digits, `_twins`) are one box: one side stays in its row, the other goes half a row lower. Several squares in a row (two spines, many leaves) are left alone.
- **End points in the Overview** (`layout.groups_of(..., follow=True)`, `_follow_neighbours`). Devices nobody captured that fit no site (phones, PCs, access points, a switch behind a distribution switch) move into the one site their visible cables lead to, in up to `FOLLOW_PASSES` passes; a device linked to two sites stays in "Other devices". `auto_mode` counts sites with `follow=False`.
- **F5 neighbors without LLDP** (`f5neighbors.assume_f5_neighbors`, called after `infer_neighbors` in `service.build_topology`; `inferred._arp_peers` skips a BIG-IP because its ARP table names VLANs, not ports). How it is read:
  - VLAN to ports: the VLAN table (`l3facts["f5"]["vlans"]`), a trunk expanded to its member ports; ports that are down are left out when another is up (`port_state` from `show net interface`).
  - A **first-hop-redundancy virtual MAC** in the ARP table marks the gateway of that VLAN. HSRP v1 `0000.0c07.acXX` (XX = group, hex) and HSRP v2 `0000.0c9f.f000` to `0000.0c9f.ffff`: https://www.cisco.com/c/en/us/td/docs/switches/datacenter/nexus3000/sw/unicast/503_u1_2/nexus3000_unicast_config_gd_503_u1_2/l3_hsrp.html (protocol: https://www.rfc-editor.org/rfc/rfc2281). VRRP IPv4 `00-00-5E-00-01-{VRID}`: RFC 5798 section 7.3, https://www.rfc-editor.org/rfc/rfc5798. GLBP uses the prefix `0007.b400`; Cisco's guide only shows examples (`0007.b400.0101`), so only the protocol is named, no group (https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9400/software/release/17-11/configuration_guide/ip/b_1711_ip_9400_cg/configuring_glbp.html).
  - The next hop of a static route or the default route is a gateway too (the route table is in `l3facts["routes"]`, with the `default` flag); when no ARP entry is left for it (ARP entries expire), the VLAN whose self IP subnet contains it says where it is.
  - An address alone on a /29 to /31 self-IP subnet is the router at the other end; the VLAN name `ISP`, `WAN`, `MPLS`, `METRO`, `INTERNET` makes it a cloud. The address on a `SYNC` / `FAILOVER` / `HA` VLAN is the HA peer: the other captured unit when both are uploaded (one line on the sync port, `_same_cable` stops the second unit adding it again), otherwise a grey BIG-IP "assumed HA peer". A BIG-IP's other ARP entries are hosts (`graph.f5_hosts`, appended to `graph.hosts` after the MAC tables; OUI 00:50:56 is VMware).
  - A gateway that is a captured device (it owns the IP address) is joined to it, with its port named when it is a routed interface; a port with a CDP / LLDP link is left alone; more than `MAX_GATEWAYS` (4) gateways behind the same ports are folded into one node (`UPSTREAM-...`), the default gateway and route next hops stay apart.
  - Evidence names on the line: `ARP`, `HSRP` / `VRRP` / `GLBP`, `ROUTE`, `VLAN`; TOPO-027 lists them and, for a BIG-IP, adds why they are assumptions. Self IPs and traffic groups: https://techdocs.f5.com/kb/en-us/products/big-ip_ltm/manuals/product/tmos-routing-administration-13-1-0/6.html; `show net arp`: https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/net/net_arp.html.
  - **Why not read LLDP.** `show net lldp-neighbors` exists (https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/net/net_lldp-neighbors.html, the page names no output fields), but the TMOS 12.1 manual says a BIG-IP interface only transmits LLDP (https://techdocs.f5.com/kb/en-us/products/big-ip_ltm/manuals/product/tmos-implementations-12-1-0/12.html) and the command printed nothing in the real captures. The reliable source of the cable is the switch the BIG-IP is plugged into: upload its capture, its CDP / LLDP table names the BIG-IP port and the dashed line becomes a real cable.
  - What stays unknown: which switch a port really reaches. A VLAN tagged on two ports is drawn as two cables to the same gateway; they may reach two different switches of one HSRP pair.
- Known limits: a lone LTM's physical page shows the gateways but no switch; orphan VDOM / guest nodes are isolated; Palo Alto aggregate-ethernet is not read; the first build of a large set takes about 45 s.
- Tests: `tests/test_topology_v08.py` (synthetic data only).

## Version 0.9: lines around site boxes, one site per chassis, Palo Alto aggregate-ethernet

- **Routing around site boxes** (`scene._route_around_boxes`, called first by `_route` when the page has group boxes). For every line between nodes of two different boxes whose straight path clips a third box: Dijkstra over the inflated corners of all boxes (`BOX_CLEAR` 14 px + `LANE_STEP` 7 px per lane, `LANES` = 5, `BEND_COST` 30), corner-to-corner edges that touch no box are cached per margin, the end-to-corner edges exclude the boxes of the two ends and the devices of those boxes. A line with no path keeps the old single-bend routing. Waypoints are stored in `page.routes` like any other multi-point route (SVG, draw.io, labels read them).
- **Sites by chassis** (`layout.groups_of`): the prefix is taken from `Device.chassis` when it is set, so all VDOM / vsys / vCMP-guest nodes of one box share a site.
- **Palo Alto aggregate-ethernet** (`panosdev`, parsers `paloalto_xml`, `paloalto` (set), curly view via the XML tree): `PaInterface.interface_type == "aggregate"` with `lacp_enabled`, `lacp_mode`; member ports carry `aggregate_group`. `Device.bundles` / `bundle_of` / `bundle_info` are filled like a FortiGate aggregate; members follow the group's vsys (`_owner`).
- Known limits: the first build of a large set takes about 40 s (85 % is the Switch Analyzer's per-capture reading, cached for the next build); a lone LTM has no switch to draw until the switch capture is added; vCMP guests sharing one physical port still attach to the first guest; the L3 over L2 page can place a "next-hop routers not captured" node between two devices.
- Tests: `tests/test_topology_v09.py`.

## Version 1.0: comb lines to end points, Palo Alto HA and Panorama exports, ports described twice

- **Comb routing** (`scene._route_comb`, called from `_route` after `_route_around_boxes`, not on curved pages). Lines between a switch (the owner of the frame, or any device outside it) and an end point inside a frame (`Placed.box`) become: head (leave the icon side at `COMB_EXIT` steps) -> drop at `COMB_CLEAR + COMB_STEP * rank` px beside the switch -> lane `lane_step` px apart above the frame -> channel beside the column (`COMB_CHANNEL` px between lines sharing it; the strip on the switch side of the column, or on its far side when that strip lies where the lines drop) -> end point. Per side of the switch the lines are sorted by the x-distance their lane reaches (first-row lines: the end point, others: the channel) and take lanes and drops in that order, outermost = highest lane = leaves highest: this nesting makes crossings impossible within one switch. A line is kept only when `_comb_free` finds no other device on it, and a switch whose lane room is below `COMB_LANE_MIN` keeps straight lines. `layout._gaps` adds `4 px * lines - 20` (max `COMB_EXTRA_MAX`) to the row gap above a frame so the lanes fit. Lines directly below the switch stay straight.
- **Palo Alto HA** (`panosdev` reads `config.ha` into `l3facts["pan_ha"]`; `panha.assume_pan_ha` adds peer and links, called in `service.build_topology` beside `assume_f5_neighbors`). The parsers fill `PaHa` (`paloalto_xml._parse_high_availability`, `paloalto._apply_ha_line`). Link evidence `HA`, state `inferred`; ports of a captured pair are matched by role; a port already cabled by CDP / LLDP is not drawn again. Docs: https://docs.paloaltonetworks.com/pan-os/11-1/pan-os-admin/high-availability/ha-concepts/ha-links-and-backup-links
- **Role guard** (`roles.classify`): a node whose reader gave `role_hint` firewall or loadbalancer and a vendor is not re-classified.
- **Port hints and double claims** (`inferred.port_hint`, `claimed` map in `infer_neighbors`, finding TOPO-029 in `findings._inferred_findings`).
- **Label placer, second search** (`labelplace.WIDE_FRACTIONS`, `WIDE_SHIFTS`): when the best first-pass spot still scores 4 or more (on a device, a caption or another label), every 4 % of the line is tried with shifts up to 160 px; the score adds `|shift| // 28` so the nearest free spot wins. `CHAR_W` 5.4.
- **Satellites** (`satellites._swap`, `_plan_cost`): after the greedy placement, pairs of extras of the same kind (`Extra.above`) exchange spots when the summed line length plus `HIT_COST` (400) per line through another node's icon + caption falls; at most `SWAP_MAX` 36 extras, `SWAP_PASSES` 4. **L3 arcs** (`l3over2._bow_candidates`, `_touches`): the planned bow, its mirror, then +40 / +80 px on both sides; a candidate must clear every other node and not lie within 24 px of a sibling's bow; none fits = the planned bow.
- Known limits: a switch with very many end-point lines whose frames lie below other rows (core stack with 90 learned hosts) keeps diagonals where a device is in the way; the HA cable is assumed direct.
- Tests: `tests/test_topology_v10.py`.

## Version 1.1: comb routes keep their direction, drops for the middle column, no reversing lane

- **Route orientation** (`scene._route_comb`): `page.routes[index]` runs from `connection.a` to `connection.b` (the convention of `labelplace`, `svg` and `drawio`); the comb builds its path from the switch, so the path is reversed when the end point is `connection.a`. 1.0 stored it switch to end point for every line, which drew a triangle (end point, bend beside the switch, far lane, bend above the end point, switch) for every line written end point first.
- **Order and reach** (`scene._comb_order`): for one side of a switch the lines are sorted by signed reach, `side * (x of the lane's far end - x of the switch)`, nearest first; rank r drops at `COMB_CLEAR + drop * r` and needs `reach - 6` beyond that, otherwise the drops are pulled together (from `min(COMB_STEP, 360 / lines)` down to `COMB_STEP_MIN`) and, if that is not enough, the line takes the far strip (`tx + side * (COMB_OUTER + COMB_CHANNEL * k)`, `COMB_OUTER` 64) instead of the strip toward the switch (`tx - side * (step / 2 + COMB_CHANNEL * k)`). The drop of a line is `min(COMB_CLEAR + drop * rank, reach - 6)`: a lane only runs outwards. A line that still has no room beside the switch (`reach - 6 < COMB_CLEAR`) stays as the earlier routers left it.
- **Middle column**: an end point of a frame with `|dx| <= 6` from its switch and an end point above it in the same column is a `centred` line: it takes the side with fewer lines, nearest ranks first (the deeper the row the higher the rank), `off = sx + side * (COMB_CLEAR + drop * rank)`, path = head + `(off, ty)`, so five points from the switch to the end point.
- Known limits: unchanged from 1.0 (a switch with very many end-point lines whose frames lie below other rows keeps diagonals where a device is in the way; the comb is not drawn on curved pages). A line that has to take the far strip of its column enters the end point from the outer side, one hook of about 60 px.
- Tests: `tests/test_topology_v11.py`.

## Version 1.2: dense frames, curved comb, labels on drops, bridges, BIG-IP lanes

- **Wall limit** (`scene._comb_wall`, `_comb_order(..., limit)`): the first box beside the switch in the band between the switch and the lanes gives `limit` (px from the switch centre, minus 6); the drop of rank r is at `sx + side * min(COMB_CLEAR + drop * r, reach - 6, limit)`. `_comb_order` first shrinks the drop step (`room = (limit - COMB_CLEAR) / (lines - 1)`, floor 4 px, 2 px when a wall limits), then moves the first violating line to the far strip; a switch whose `limit < COMB_CLEAR + 2` keeps the old routes. `_comb_free` still rejects any path through a device.
- **Curved pages**: `_route_comb` runs on every page; `curve_routes` turns only single-point routes into curves. `svg._rounded_path` (quadratic corners, radius up to 9 px and never more than half of a run) draws comb lines on curved pages; draw.io writes `rounded=1;arcSize=12` and all waypoints (`drawio._add_edge(..., comb)`; `page.curved and n in page.comb_source`). `l3over2` carries `comb_source` through `kept_index`.
- **Port labels on drops** (`Page.comb_source`: connection index -> switch end; `labelplace._on_the_drop`): the label of the switch end is centred on the vertical run `run[2] -> run[3]` (centre, icon edge, beside the icon, drop), first free height from the top, `DROP_STEP` 5 px between two labels; falls back to the normal search when no height is free.
- **Bridge** (`scene._route`, `BRIDGE_END` 60): for a blocked link longer than `3 * BRIDGE_END` on a non-curved page the route is two corners, each `BRIDGE_END` px along the line from its own device and lifted by `lift` (0, then +-70, 140, 220, 320 px) perpendicular to it, the first lift whose three segments hit no device; V peaks (one bend) are gone. Curved pages use `CURVE_POINTS` as before.
- **F5 map lanes** (`f5page._top_lanes`, `ShapeEdge.points`): per side (TL, TR) the boxes are ordered by row (higher row nearer the middle trunk) and column; trunk x = `centre_x + sign * (2 + step * rank)`, lane y = box bottom + 3 + `lane_step * col`; path = BIG-IP top, trunk, lane, box bottom centre. `svg` draws `ShapeEdge.points` as a polyline, `drawio` as `Array as="points"`. `svg._fit` cuts names to the box width with an ellipsis.
- Known limits: a far-strip line still enters its end point from the outer side with one hook (about 10 % of the lines on random sets); the dense L3 page of two aggregation switches with about 30 SVIs is unchanged; a wall closer than `COMB_CLEAR + 2` px keeps diagonals.
- Tests: `tests/test_topology_v12.py`.

## Version 1.3: switches over their frames, foreign frames as obstacles, a column for the small sites

- **Owner centring** (`layout._arrange`, nested `centre_owners`): after all rows are placed, for each row (except star rows at tier <= `STAR_MAX_TIER`) the switches that own a frame of end points are moved to the middle of that frame. The frame centres are frozen, so the pass runs once; `_spread(row, want, gap, gaps)` fits the wanted x with per-pair gaps (isotonic fit on offsets, identical to the old result for uniform gaps). A switch whose frame is several rows below gets a dummy channel item of `DROP_ROOM` px so the comb of that frame has a free lane through the rows between (`drop_reach`, `_owner_gaps` size the gap from the number of lines, `DROP_CLEAR` 62, `DROP_STEP` 12 down to `DROP_STEP_MIN` 4, `DROP_SPAN` 360). Rows after the first changed row are re-laid with `top_down` unless they are frame-kid rows.
- **Frames as obstacles** (`scene._frames`, `_route`): for a line that is not one of a frame's own lines the frame rectangle is added to the obstacles; the lifts `[0, +-70, +-140, +-220, +-320]` get `[+-460, +-620]` only when a frame is in the way; if still blocked the route is retried without the frames (`_detour`).
- **Dominant site** (`scene.HUB_DOMINANCE`, `_side_stack`, `_arrange_groups`): the largest site by area, not the one with the most links, becomes the hub when its area is at least twice the others'; the others form one column at `x = hub width + BOX_PAD`, ordered by `_side_stack` (greedy by link weight to the previous box), "Other devices" last.
- Checks: `tests/test_topology_v13.py` audits random core + access-switch graphs for collinear shared stretches between different switches and for lines inside foreign frames, owner position over the frame centre, width bound, determinism, the site column order and `_detour`.

## Version 1.4: middle column under the switch, approaches untangled, bigger reading cache

- **Even grids** (`layout.frame_columns(count)`: up to three icons in one line, then `ceil(sqrt(count))` up to `BOX_COLS_MAX` = 6): when `cols` is even and the frame has more than one line, `centre_owners` adds +-0.5 step to the frame's centre (the side the switch already leaned to), so the switch stands over a column. `centre_owners` now also handles a row that holds one switch (`shifted`), and remembers the rows it centred (`changed`) so the later `top_down` pass does not move them again. ## Version 1.6: one line per pair of sites, grouped shared subnets, a warning for unreadable single diagrams, captures to take next, anonymized copy

- **One line per pair of sites on the Overview** (`scene.SITE_BUNDLE_MIN` 3, `scene.bundle_sites`): when three or more separate device-to-device cables join the same two site boxes, the Overview draws one line labelled "N links". - **Shared subnets that have the same devices on them are one node** (`l3engine.group_segments`, `SEGMENT_OVER` 4): three distribution switches with thirty VLAN interfaces each gave thirty ellipses and ninety lines; the L3 page now draws one node "30 shared subnets" (with the subnet range) and one line per device (ids `L3-G01`, ...). Every subnet keeps its row in `l3-links.csv` (plus one row per group), in the trace and in the click panel. The option "Group what repeats on the L3 pages" switches it off (and also the grouping of uncaptured next-hop routers).
- **A forced single diagram that is too large says so** (`service.grouping_notices`, `WIDE_DIAGRAM_PX` 12000, `LARGE_DIAGRAM_DEVICES` 150): with "One diagram" chosen, a result wider or taller than 12,000 px or with more than 150 devices gets a notice with its size and the number of sites "Automatic" would draw (or, when the hostnames give no sites, the advice to build each site as a run). The notice is on the page, in `run-settings.txt` and in the report.
- **Owner switches stand nearer their frames** (`layout._spread` `follow_weight`): when switches without a wish sit between frames, the switches that do wish something share the move instead of all of it falling on one (the owner row of item 4).
- **Faster first reading of large sets**: the ACL reference scan, `clean_lines` and the fingerprint use a single compiled pass; the output is identical (tests compare the old and new reading), about 10 % faster on a typical capture and up to 35 % on configurations with long ACLs. Multiprocessing was not added: on Windows each worker re-imports the application and the gain is small.
- **100 captures in about 8 seconds** (was 26): `labelplace._LineIndex.crossed` stops counting at the score a spot must beat and the caller skips the line check for a spot that cannot win, and `scene._hits` tests only the boxes near the segment. The label positions are identical (`tests/test_topology_perf.py` compares the shortcuts with the plain loops). A set of 100 invented captures (about 270 KB) is the benchmark; time `build_topology` for it after changing either function.
- **Captures to take next** (`priority.capture_priority`): the tab "Capture next", the table `capture-priority.csv`, the workbook sheet "Capture next" and section 6 of the report list the devices whose capture would add the most. "New capture" rows are devices that captured neighbors see but nobody captured; they are ranked by the links a neighbor table reports (links only inferred from ARP, descriptions or routes count after those), then by the number of different captured neighbors, then by the MAC addresses learned behind them, then by name. "Capture again" rows are captured devices without a CDP / LLDP neighbor table. Each row names the ports seen, the reason, and the collect list in `static/collect-scripts` that fits the vendor and model (only files that exist; when the vendor is not known the row says so).
- **Anonymized copy** (`anonymize.py`, option "Also make an anonymized copy"): a second pack `keystone-topology-pack-anonymized.zip` built from the saved device state with every name and number replaced, and the key `anonymization-map.csv` that stays on your computer.
  - Replaced, consistently in every picture and table: hostnames, domain names, port descriptions, VRF and F5 object names, the topology name and the provider hints (word by word, to another word of the same length and letter / digit pattern, never a role word); IPv4 and IPv6 addresses (prefix-preserving: two addresses that shared a /24 or a /16 still do, point-to-point peers stay peers, private stays private and public stays public, masks and wildcards are kept, the last octet is kept so `.1` is still `.1`, link-local stays `fe80::/64`); MAC addresses in dotted, colon, hyphen, Huawei and bare notation (the vendor prefix is kept, multicast and FHRP virtual MACs are kept); serial numbers (same length and pattern).
  - Kept, because the picture depends on them: role words, vendor, model and software version, interface and port names, VLAN ids, speeds, protocol names, special addresses (0/8, 127/8, multicast).
  - The twin is built again from the pseudonyms, so links, roles, sites, findings and L3 edges are computed, not edited. On sixteen real captures (not in the repository) the anonymized twin had the same counts of devices, links, findings, pages and L3 lines as the original.
  - A scan of the finished files for any original word, serial or MAC (and of the saved state for any original address) is part of every export; what it finds is written into the key file as `LEFTOVER` rows and shown on the page.
  - Limits, stated plainly: the shape of the network (how many devices, how they are linked, which vendors and models, the VLAN ids, the vendor prefixes of MAC addresses, the last octet of addresses) is not hidden, and a person who knows the network may recognise it from that. Technical words that come from device output (platform and capability strings in CDP, feature names) are not names and stay. Every export uses a new random key, so two exports of the same captures do not match each other. The anonymized `topology.json` can be loaded as a previous run, but not together with the originals of the same devices. Treat the key file as sensitive as the captures.
- Tests: `tests/test_topology_v16.py` (bundles, grouping, notices, spread, speed, priority) and `tests/test_topology_anonymize.py` (addresses, MACs, serials, words, structure of the twin, leftover scan, the download), synthetic data only.

## Version 1.7: lines lifted apart, room for tall frames, one frame for the access points of a switch

- **`scene._lift_apart`** (called last in `_route`, before curves): runs between two corners that lie within `LIFT_SAME` (2 px) of each other over more than 8 px are separated; the later line (comb lines first, then by index) moves both corners of the run by `LIFT_STEP` (8 px) times 1, -1, 2, -2, ... to the first track with no other run within `LIFT_ROOM` (4 px) and no device on the whole line (`_comb_free`). It repeats up to four times.
- **Frame pitch and lane room** (`layout.frame_pitch`, `FRAME_PITCH_MAX` 1.9; `layout._gaps`, `COMB_LANE_ROOM` 7, `COMB_EXTRA_MAX` 700, `COMB_FIXED` 190): the distance between frame columns grows with the rows of a column; the row gap above a frame grows with the lines of its comb. `layout._pin_channels` pins the "channel marks" of a core so devices in the rows between it and its frame do not take the room of its drops (`PIN_GAP_MIN` 0.8).
- **Heads** (`scene.COMB_EXIT_MIN` 4, `COMB_EXIT_SPAN_MAX` 52): the heads of one side of a switch with more than five lines leave along up to 52 px of the icon's side, the highest above its corner, and no two closer than 4 px.
- **Ragged last row** (`scene._route_comb`): the end points of a short last row stand between two columns of the full rows, so their channel uses the narrow strip (`channel_for(step)`); the others use the strip of the full pitch (`channel_for(wide)`).
- **Framing** (`layout.box_groups`): `seen` holds the neighbours a cable really shows; an end point with one such neighbour and others only inferred is framed under it. Inferred lines into a frame are no comb lines; `scene._route_into_frames` takes a list of strips (target's side first) and two shapes per strip (straight, or down from the source 18 px aside and along the frame's top), `scene._detour_least` is the fallback of `_route` when no detour is free.
- **Frame names** (`titles.end_title_spot`, `page_label_rects`): the name slides to a gap with no line and no port label; `svg` and `drawio` call the same function.
- Tests: `tests/test_topology_v17.py` (35), synthetic data only. Measured on nineteen real runs and the stored packs: see the changelog entry "Topology Builder 1.7".
- Known limits: a guessed second cable that enters a frame can add crossings with the comb of the other switch; bundle lines between sites on the Overview that no detour frees still take the way through the fewest devices.

## Version 2.1: lone end points come back, a reported cable beats a description, hypervisors are servers

- **`layout._bring_lone_ends(row, framed, frame_of, neighbours, index_of, index, graph, spot, xstep, slots)`**, called from `centre_owners` for every row that holds frame members.  Units are lone single-neighbour end points, or frames of at most `LONE_FRAME_MAX` (3) members, whose switch is more than one row up and farther than `LONE_FAR` (6.0) icon steps away; each unit is cut out of the row and put at the cut boundary (never between two members of one frame) whose middle is nearest its switch, then the row is fitted again with `_spread_framed` (frames as units, order kept).  A kid row must never go through `_spread`: the frames' half-widths are lost.
- **`inferred.SINGLE_HOMED = ("ap", "phone")`**: a guess made from a port description only (`how <= {"DESC"}`) is not drawn when the named device is an access point or phone that a neighbour protocol already reports on another switch.  The guess becomes a `description-elsewhere` fact, listed in TOPO-028.  ARP and MAC guesses are unchanged; so are servers and switches (they may be dual-homed).
- **`roles._DESCRIPTION_RULES`** (applies to uncaptured devices before capabilities): server and access-point patterns extended (see the changelog). 
- **`scene._route_comb`**: `full_pitch[parent]` is the most common gap of the full line, so the half-step offsets of the short last line cannot shrink the channel strip.
- **`scene._detour_apart` / `_ride`**: a bridge that would lie more than `LONG_RIDE` (60) px on a routed line takes the next lift that gets round the obstacles and adds no crossing (`_crossings_of`); when every lift rides, the first one stays.

## Version 1.8: child switches follow their parent, a guessed cable chooses the way in with the fewest crossings

End points that stand loose are not moved.
- **`scene._route_into_frames`**: candidate paths per strip are the straight line `[(gate, top), (gate, ty)]` and the elbows `[(sx +/- off, top), (gate, top), (gate, ty)]` for `DROP_OFFSETS` (18, 105, 60, 150 px); when the source is more than `TALL_DROP` (260 px) above the frame the elbows come first. ## Hierarchy: core, distribution and access

Switches are drawn as a tree under their core.  `roles.infer_hierarchy` (called at the end of `roles.classify`) finds the core of every group of linked switches and sets `Device.hier_depth` (hops from the core; the core is 0), `layout._tier_values` turns that into rows (`roles.DEPTH_ROWS`: core 1, then 2, 3, and a little more room for very deep chains; end points stay from row 4), `layout._centre_parents` puts every switch over the middle of its children (the last switch of a branch over the end points that hang on it alone), and `scene._route_fan` draws the lines to the switches below out of the side of the parent.

- **A plain `SW` states no tier.** `MKS-SW1`, `BAL-SW2` say "a switch", not where it stands, so `roles.role_from_name` is false for a name whose only role word is the generic `SW` and the shape decides (`roles._TIER_WORDS` lists the access words that do state a tier: `ACC`, `ASW`, `TOR`, `SWAC` ...).  A star (SW1 with two downlinks) is then drawn with SW1 as the core and SW2 and SW3 in the row under it, each over its own end points; a chain SW1 - SW2 - SW3 has no middle that wins and stays flat.
- **Role from the host name** (`roles._WORD_RULES`): `SWCO`, `SWCODI`, `SWCORE`, `CORESW`, `CSW`, `COSW` core; `SWDI`, `SWDS`, `SWDIST`, `SWAGG`, `DSW`, `DISTSW`, `AGGSW` distribution; `SWAC`, `SWAS`, `SWACC`, `SWACCESS`, `ASW`, `ACCSW` access.  These are role words for the anonymized copy as well, so the twin keeps the same structure.
- **Role from the shape** (only for a switch whose name gave no role): a group needs at least three switches (two when a core is known).  The core is, in this order of preference, a switch already known as a core, then the one linked to a router, firewall or load balancer, then the one with the fewest hops to the farthest switch of the group, then the one with the most links.  Two peers of a vPC / MLAG pair that tie are both the core; any other tie leaves the group as it was, because a wrong guess is worse than none.  From the core: a switch with another switch one hop further is a distribution switch, one with none is an access switch.
- **Rows by hops, not by name.** A switch linked straight to the core is in the row under it whatever it is called (an `SWAC` switch on the core stands beside the `SWDI` switches), so no line jumps over a row.
- **Parents over children.** From the deepest row up, a switch moves to the middle of its own children (a switch with two parents belongs to the nearer one); a switch with nothing under it follows the one before it.  A row that holds a router or firewall with lines to the rows below keeps its places.
- **Fan lines** (`scene._route_fan`): out of the side of the icon, along under it, then straight down, each line of one switch on its own height (`FAN_EXIT` 20 px apart along the side of the icon, the farthest highest); not used for a switch right below its parent, a switch with two parents or a line that would hit a device.
- Layered design (access, distribution, core): https://www.cisco.com/c/en/us/td/docs/solutions/Enterprise/Campus/HA_campus_DG/hacampusdg.html
- Known limits: the shape rule works from links only, so a ring of equal switches (no middle, no router) is left flat; a switch with two parents is drawn under the nearer one and keeps the ordinary line to the other; chains of more than six hops share the last rows.
- Tests: `tests/test_topology_hierarchy.py`, `tests/test_topology_star.py`.

## Export clean-up

Each build writes its tables, drawing, trace file and packs to `exports/topology/<run id>` (32 hex characters, about 2 MB). The folder is read by the download links and by `/api/trace` of the page that built it, by the Topology history panel (`/api/history`), and by the Compare two runs and Cutover runbook panels (`/api/runs`, `/api/diff`, `/api/runbook`), nothing else; the reading cache is in memory. `features/topology/retention.py` (`prune_runs`) keeps the folder small:

1. Only folders whose name is a run id are looked at.
2. The newest `TOPOLOGY_KEEP_RUNS` (20) stay; a run older than `TOPOLOGY_MAX_AGE_DAYS` (30) goes whatever the count. Both are constants in `app.py`, passed on through `app.config`. The age is the modified time of the run folder; the history panel puts that time back after every change it makes, so renaming or pinning an old run never makes it look new.
   A run with a `_pinned` marker file (set by the Pin button) is never removed and does not count toward the 20; at most `history.MAX_PINNED` (30) runs can be pinned.
3. The run just built (`protect`) and any run younger than `GRACE_SECONDS` (600) are never removed and count toward the limit, so two builds at the same time cannot remove each other's files.
4. A run folder with no file in it is removed and does not count.
5. It runs at start-up (`app._prune_topology_exports`) and after every build, and never raises: a file that Windows still holds open is skipped and goes at the next pass.

The start-up sweep of `app.py` (`_sweep_directory`) removes files older than 30 days from `exports`, `uploads` and the Device Operations backups, then the empty sub-folders that are also older than 30 days, deepest first. The folders themselves and `.gitkeep` stay. `exports/topology` is skipped (`skip=`): it has the rules above, and a pinned run must keep every file however old it is.

A run folder can be deleted by hand at any time while Keystone is stopped; the only effect is that a download link or path trace of that old page answers "This export has been removed. Build the topology again." The folder `topology module result` is not part of Keystone and is never touched.

## Topology history

The **Topology history** button beside the topology name opens a dialog with every run kept in `exports/topology` (newest first, with a count on the button). `features/topology/history.py` does the work and `routes.py` serves it; the page script is `static/js/topology-history.js`.

| Action | Route | What it does |
|---|---|---|
| List | `GET /topology/api/history` | Applies the clean-up rules first (Keystone can stay open for weeks), then returns runs with name, build time, devices, links, findings, size, pinned, "kept until" date and whether the pack ZIP exists (`has_pack`, which shows the **Download pack** button on the card), plus the rules (`keep`, `max_age_days`, `max_pinned`) and the disk used. The page also shows the age of each run ("2 hours ago"). |
| Details | `GET /topology/api/history/<id>` | Counts, vendors and roles, the build options, the first findings and the files that can be downloaded (pack ZIP, report, draw.io, Excel, anonymized pack, tables). Downloads use `/api/export/<id>/<name>`. |
| Pin / unpin | `POST /topology/api/history/<id>/pin` `{pinned}` | Writes or removes the `_pinned` marker. Pinned runs are exempt from the clean-up. |
| Rename | `POST /topology/api/history/<id>/rename` `{name}` | Writes `_name.txt` with the same rules as the name field (letters, digits, dot, dash, underscore; 60 characters). The report title inside the pack keeps the name it was built with. |
| Note | `POST /topology/api/history/<id>/note` `{note}` | Writes `_note.txt` (plain text, at most three lines and 300 characters, control characters dropped; an empty note removes the file). The note is listed with the run, searched by the panel and shown as text (never as markup). It is **not** put in the documentation pack, so it stays on this computer. Like pin and rename it does not change the age of the run. |
| Delete | `DELETE /topology/api/history/<id>` | Removes the whole run folder. The page asks once more before it sends this. |
| Delete all unpinned | `POST /topology/api/history/clear` `{include_pinned}` | Removes every run except pinned ones and a build still writing its files. |

Compare and Cutover runbook are not repeated: the dialog sends the browser events `tp:compare` (two run ids; the older is "before") and `tp:runbook` (one run id) to the Compare and Runbook tabs, which come to the front with those runs chosen. After a build, `topology.js` sends `tp:built` so the count on the button is refreshed.

**Open again.** Every build also keeps the answer the page was given (tables, diagrams, findings, downloads) as `_result.json.gz` in its run folder (gzip, a few hundred KB; not a download). The details of a run offer **Open again** when that file exists: `GET /topology/api/history/<run id>/result` returns it unchanged, the dialog sends `tp:open`, and the Create tab shows the result exactly as after the build, without reading a capture or building anything. A run built before this existed has no such file (`has_result` is false in the list) and is built again from its captures; a damaged file, one that belongs to another run or one that unpacks to more than 64 MB is refused the same way. The file is deleted with its run.

**Search, filter, sort.** The search box looks at the name, the note, the build time and the view. *Show* narrows the list to pinned runs, runs that are not pinned, runs with medium findings or runs with a note; *Sort by* offers newest or oldest first, name, most findings (medium first) and most devices. The sort choice is remembered in the browser; the baseline mark stays on the run that has it. Nothing here changes what is kept: the clean-up rules above apply to every run, shown or not.

How it stays small and safe:

- Each build writes `_meta.json` (counts, vendors, roles, first findings, build options; no capture text and no address) next to its other files. A run built before this existed gets its `_meta.json` the first time it is listed, read once from `topology.json`. Listing twenty runs therefore does not read twenty files of several megabytes.
- Every id is checked against the run-id pattern (32 lower-case hex characters) before a path is built, and a folder that is a symbolic link is ignored, so an id can never leave `exports/topology`. State-changing requests pass the same cross-site guard as the rest of Keystone (`core/local_guard.py`).
- The history holds real host names and addresses of the network on this computer only; Delete all unpinned and the per-run Delete remove them. The anonymized pack is the file to share.
- Tests: `tests/test_topology_history.py`, `tests/test_topology_retention.py`.

## Audit evidence

The documentation pack carries what a change record or an audit asks of a network diagram (`features/topology/evidence.py`):

- **`MANIFEST.sha256`**: the SHA-256 of every other file in the pack, in `sha256sum` format (`sha256sum -c MANIFEST.sha256` on Linux, `shasum -a 256 -c` on macOS, `certutil -hashfile <file> SHA256` on Windows). A file changed after the build no longer matches.
- **The pack hash**: the SHA-256 of the ZIP itself is written next to it (`keystone-topology-pack.zip.sha256`, not a download) and shown in the details of the run in the Topology history, to be written into the change record. The manifest cannot vouch for itself; this one value does.
- **`audit/inputs.sha256`**: the SHA-256 of the text of each capture the run was built from (UTF-8, after a ZIP is unpacked), so the same captures can be shown to give the same pack. The anonymized pack does not carry it (the file names are originals).
- **`audit/controls.csv`**: the drawing and every finding, each with the control it is evidence for. The drawing supports PCI DSS v4.0 1.2.3 (an accurate network diagram), CIS Controls v8 12.4 (architecture diagrams), ISO/IEC 27001:2022 A.8.20 and NIST SP 800-53 CM-2, and with the inventory CIS 1.1, NIST CM-8, ISO A.5.9 and PCI DSS 12.5.1. Findings are tagged by what they look at: discovery and inventory findings to the inventory controls, configuration mismatches (trunks, speeds, duplex, native VLAN, STP, MTU, OSPF) to NIST CM-6, CIS 4.1, ISO A.8.9 and PCI DSS 2.2.1, and redundancy findings (single uplink, vPC, oversubscription) to NIST CP-8(2) and ISO A.8.14. Keystone tags what a finding is evidence for; it does not assess compliance, and the file says so.
- `audit/README.txt` explains the three files.

References: CIS Controls v8 https://www.cisecurity.org/controls/v8 ; NIST SP 800-53 Rev. 5 https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final ; PCI DSS https://www.pcisecuritystandards.org/document_library/ ; ISO/IEC 27001 https://www.iso.org/standard/27001 . Check the edition your auditor uses: the identifiers are those of the editions named above.

Tests: `tests/test_topology_evidence.py`.

## Baseline banner

The newest pinned run in the Topology history is the **baseline**. After every build the page asks `GET /topology/api/baseline/<run id>` and shows a banner above the result: *Same as the baseline*, or *N differences from the baseline, M to read* with **Show changes** (opens Compare two runs on the two runs and runs it) and **Dismiss**. Nothing is shown when no run is pinned. The history marks the baseline with a badge, and its Details have **Compare with the baseline**. The endpoint uses the same engine as `/api/diff` (`compare_runs`), so the numbers are the ones the comparison table shows, but it does not write an activity-log entry for every build. An answer for an earlier build never replaces the banner of a newer one, and a new build or **Clear** removes the old banner at once. Tests: `tests/test_topology_demo.py` (baseline part).

## Progress bar

The Build button starts a bar under the options: stage name, percentage, the step (capture n of N, page n of N) and the seconds so far. `features/topology/progress.py` holds the stages and their share of the bar (reading captures 66, matching links 4, pages 12, L3 views 6, diagram files 5, tables and pack 7); `service.read_devices`, `build_topology` and `routes._write_run` call `progress.report(stage, fraction, detail)`, which does nothing when no one listens. The page polls `GET /topology/api/progress/<id>` (id = the `progress_id` form field, 8 to 64 letters, digits, `_` or `-`; builds are kept for 30 minutes, 64 at most, in memory only). The bar never moves back; with an anonymized copy the first pass owns 0 to 55 % and the copy 55 to 100 %.

## Compare two runs

The **Compare two runs** tab (second tab of the Topology page) shows what changed between two builds. `features/topology/diff.py` reads the tables of two `topology.json` files and `routes.py` serves them: `GET /topology/api/runs` lists the runs still kept in `exports/topology` (newest first, with name, time, device and link counts), `POST /topology/api/diff` takes `before` and `after` as uploads (a `topology.json` or the whole `keystone-topology-pack.zip`) or `before_id` / `after_id` for kept runs, and returns the summary, the rows and a CSV. The page script is `static/js/topology-diff.js`; the CSV is built by the server so the download has the same columns as the table.

What is compared:

- **Devices**, by name: added, removed, and a change of role, vendor, model, software version, management address, serial numbers, stack size, vPC domain and role, captured or only seen by neighbors, and the captured commands (`has_*`).
- **Links**, by their two ends (device and port, alphabetical, so the order a run wrote them in does not matter, and the per-end columns follow their end). Added, removed, **moved** (a removed and an added link that are the same cable seen again: they share one end and the other end is on the same device, or they join the same two devices through other ports and are the only such pair), and a change of state, protocols, bundle, kind, vPC id, subnet, native VLAN, and per end speed, rated speed, port state and duplex.
- **Findings**, by id and device list: new, resolved, a change of severity, and one row (not a pair) when a finding that covers a list of devices, such as TOPO-004, keeps its id while its list changes.
- **Hosts** by MAC address (added, removed, moved to another switch or port, changed address or VLAN) and **Behind devices** by (device behind, switch, port): changed MAC count and VLANs.

A row is marked *need attention* when it is a loss or a risk: a device or link that disappears, a device that is no longer captured, a link seen from fewer ends than before or with the two ends in conflict (`confirmed` > `single` > `inferred` > `conflict`), a speed drop, a port that was up and is not, a port that leaves its bundle, a bundle, duplex, native VLAN or vPC id that changes between two known values, a new management address, a vPC role change, a new medium finding and a finding whose severity goes up. A value that is empty in the first run and filled in the second is a better capture, not a change to read. The rest is information. Hosts never need attention: virtual machines move and MAC tables age.

A device that is in the first run and not in the second may only have been left out of the second capture set; the summary shows how many devices were captured in both runs. An area with more than 3000 rows keeps the first 3000 in the table and says how many are cut; the CSV carries the same rows. Nothing is stored: both files are read, compared and dropped.

Documentation behind the "needs attention" rules: duplex and speed negotiation, Cisco, "Configuring and Troubleshooting Ethernet 10/100/1000Mb Half/Full Duplex Auto-Negotiation" (https://www.cisco.com/c/en/us/support/docs/lan-switching/ethernet/10561-3.html); LACP bundles, Cisco, "Troubleshoot Link Aggregation Control Protocol" (https://www.cisco.com/c/en/us/support/docs/lan-switching/link-aggregation-control-protocol-lacp-8023ad/221051-troubleshoot-link-aggregation-control-pr.html); how neighbors are learned, IEEE 802.1AB (https://1.ieee802.org/maintenance/p802-1ab-2016-revision-station-and-media-access-control-connectivity-discovery/).

Tests: `tests/test_topology_diff.py`.

### How TOPO-031 to TOPO-034 read their facts

`features/topology/l2findings.py`. The extractor (`extract.py`) keeps four compact facts per device, all also saved in `topology.json` so an "Add to a previous run" keeps the findings: `port_allowed` / `port_active` (trunk port to the VLAN list as printed, blanks removed), `stp_root_for` (instances where the capture says this bridge is the root), `stp_root_default` (the subset with default priority), `stp_protocol`. No MAC addresses are stored, so the anonymized copy has nothing extra to scrub. A fact the capture does not hold is not a finding: no trunk table, no `show spanning-tree`, no interface speeds, or a link whose other end was not captured gives no row. The oversubscription figure uses `actual_speeds` of the ports that are up (`show interfaces status`, AOS-CX `show interface`, BIG-IP `show capture`), the uplinks are the links to a higher tier of `roles.ROLE_TIER` (a down uplink does not count) and peer links to the same tier are left out of both sides.

While adding the test captures it turned out that the Switch Analyzer dropped the speed and duplex of a port that appears only in the `show interfaces status` table (a capture whose running-config has no block for that port); `_build_interfaces` now keeps them on those rows too.

Tests: `tests/test_topology_l2findings.py`.

### How TOPO-036 to TOPO-039 read their facts

`features/topology/ifparams.py` reads the `interface` blocks of the configuration in each capture (Cisco IOS XE and NX-OS, Aruba AOS-CX, Huawei VRP) and keeps, per interface, only the MTU (`mtu`, `ip mtu`) and, where OSPF runs on it, the area, the hello and dead interval, the network type and whether `mtu-ignore` is set. Which interfaces run OSPF comes from the Switch Analyzer's reading (`network` statements and interface commands, passive and shut-down interfaces left out); a value the capture does not state is the platform default. Keys, passwords and addresses are not read. The result is `Device.ifparams` and is saved in `topology.json`, so "Add to a previous run" keeps the findings. `features/topology/paramfindings.py` compares the two ends of every link whose two devices were captured, once per port-channel (a bundle member is looked at through its port-channel). An interface that runs OSPF according to a show command but has no configuration block in the capture is marked *assumed* and is not compared. OSPF on a VLAN interface (SVI) over a trunk is not compared because no single cable stands for it.

References: RFC 2328 sections 10.5 and 10.6 https://datatracker.ietf.org/doc/html/rfc2328#section-10.5 ; Cisco, OSPF Neighbor Relationship Troubleshooting https://www.cisco.com/c/en/us/support/docs/ip/open-shortest-path-first-ospf/12151-trouble-main.html ; Cisco, Troubleshoot OSPF Neighbors Stuck in Exstart/Exchange State https://www.cisco.com/c/en/us/support/docs/ip/open-shortest-path-first-ospf/13684-12.html .

Tests: `tests/test_topology_params.py`.

### How TOPO-040 to TOPO-043 read their facts

`features/topology/peerfindings.py` compares what two captured devices say about the same thing; a check needs both captures and a device that did not show the table in question is never judged. Bundles use the protocol column of the port-channel summary (`bundle_info`) and, for the modes, the `channel-group N mode` lines kept in `Device.ifparams`. The OSPF adjacency check reuses the parameters of `ifparams.py` and the neighbor rows of the Layer-3 facts (`l3facts["neighbors"]`); an interface marked *assumed* (OSPF seen in a show command, no configuration block) is skipped. HSRP / VRRP groups come from `l3facts["fhrp"]` (version, preempt, hello and hold are kept per group). Addresses come from the Layer-3 interface list. Each of the four findings is also tagged in the audit table (`audit/controls.csv`).

References: IEEE 802.1AX-2020 https://1.ieee802.org/tsn/802-1ax-rev/ ; RFC 2328 section 10.3 https://datatracker.ietf.org/doc/html/rfc2328#section-10.3 ; RFC 2281 https://datatracker.ietf.org/doc/html/rfc2281 ; RFC 5798 https://datatracker.ietf.org/doc/html/rfc5798 .

Tests: `tests/test_topology_peers.py`.

## Cutover runbook

Open the **Cutover runbook** tab (third tab of the Topology page), pick a run (still kept on this computer, or upload its `topology.json` / `keystone-topology-pack.zip`), choose the type of change (replace the hardware, upgrade the software, change the configuration), optionally a title, a window, a change record number and the devices in scope, and click **Write the runbook**. You get a printable HTML plan (open it and print to PDF) and a CSV tracking sheet (`cutover-plan.csv`: sequence, device, phase, step, command, expected result, and empty Done / By / Time columns). `POST /topology/api/runbook` does the same for scripts.

How the plan is worked out, all from the tables of the run:

- **Impact.** A device is taken out of the graph of captured links; the devices that then have no path to the top of the network (the highest tier present: provider / router, else firewall, load balancer or core) lose service and are named, with the end-host MACs learned on them. Devices that were already cut off in the run are not counted. "No loss" means a redundant path exists in the captured links, not that the traffic fits on it.
- **Order.** Edge to core (access, then distribution, then core); within a tier the device that loses fewer neighbors first; of two vPC peers with equal impact the secondary first. Treat it as a proposal.
- **vPC pairs and stacks.** A vPC peer gets a partner health check before the work and a gate before the partner may be touched; a stack is flagged as one unit.
- **Steps per device.** Reach the device, take a baseline, back up the configuration, read the open high and medium findings, confirm cabling that only one end reported, then the change (for a replacement every cable is a step, in port order, from the port map), the same commands again, and a rollback that is physical: re-patch to the old unit, previous image, saved configuration. No vendor rollback command is quoted.
- **Commands** are `show` / `display` only (Cisco IOS XE and NX-OS, Huawei VRP, Aruba AOS-CX and ArubaOS-Switch, FortiGate, PAN-OS, F5 BIG-IP); a platform without a list says so. Check them against the software version in use.
- **After the window.** Collect again, build a new run, use **Compare two runs** (before = the run of the plan), and analyze the new captures in the Switch Analyzer with a Baseline selected.

References: Cisco, Understand and Configure Nexus 9000 vPC with Best Practices (https://www.cisco.com/c/en/us/support/docs/switches/nexus-9000-series-switches/218333-understand-and-configure-nexus-9000-vpc.html); Cisco, Troubleshoot LACP on Nexus (https://www.cisco.com/c/en/us/support/docs/lan-switching/link-aggregation-control-protocol-lacp-8023ad/221051-troubleshoot-link-aggregation-control-pr.html); Cisco, Troubleshoot STP Problems and Related Design Considerations (https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/10556-16.html); Huawei CloudEngine S Configuration Guide (https://support.huawei.com/enterprise/en/doc/EDOC1100333463); HPE Aruba Networking AOS-CX VSX architecture (https://developer.arubanetworks.com/aoscx/v10.04/docs/architecture-ii-dedicated-data-center-two-tier).
